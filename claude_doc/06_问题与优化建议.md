# 六、问题与优化建议

## 6.1 潜在 Bug

### P1 — 中等

#### Bug-4：ThreadSafeQueue::front() 语义不安全

**位置：** `tools/thread_safe_queue.hpp:66-71`

**问题：** `front()` 返回值拷贝而非引用，但多次调用之间队列可能被其他线程修改，导致返回不一致的数据。

```cpp
T front() {
  std::unique_lock<std::mutex> lock(mutex_);
  not_empty_condition_.wait(lock, [this] { return !queue_.empty(); });
  return queue_.front();  // ← 返回拷贝，锁释放后数据可能被 pop
}
```

**建议：** 明确文档说明，或改为 `peek()` + `pop()` 原子操作。

---

#### Bug-5：sentry.cpp 全向感知被硬编码禁用

**位置：** `src/sentry.cpp:42-46`, `sentry.cpp:86-91`

**问题：** 使用 `#if 0` 禁用多相机初始化，全向感知逻辑被注释。当前哨兵在目标丢失时完全无恢复能力。

```cpp
#if 0  // ← 硬编码禁用
  io::USBCamera usbcam1("video0", config_path);
  io::USBCamera usbcam2("video2", config_path);
#endif
```

**建议：** 使用配置文件 flag（如 `enable_omniperception: true`）控制，而非硬编码。

---

#### Bug-6：planner.cpp shoot_offset_ 使用 auto 推导

**位置：** `tasks/auto_aim/planner/planner.cpp:347`

**问题：** `auto shoot_offset_ = 2;` 推导为 `int`，但命名带下划线后缀暗示是成员变量。实际上只是局部变量。且被直接用于数组索引。

**建议：** 重命名为 `shoot_offset` 或改为 `constexpr int shoot_offset = 2;`。

---

#### Bug-7：bullet_speed 边界检查默认值硬编码

**位置：** `tasks/auto_aim/planner/planner.cpp:274-276`

**问题：** 子弹速度边界检查 `< 10 || > 25` 时默认设为 22 m/s。该默认值硬编码，不适用于所有兵种。

```cpp
if (bullet_speed < 10 || bullet_speed > 25) {
  bullet_speed = 22;  // ← 硬编码
}
```

**建议：** 将默认值和边界设为配置项。

## 6.2 可优化点

### 性能优化

#### Opt-1：YOLO 检测未使用异步推理

**现状：** `yolo.detect(img)` 同步阻塞，CPU 等待 GPU 推理完成。

**优化方案：** 使用 OpenVINO 异步 API + 双缓冲：
```
帧 N:   infer_async(img_N)    → 等待帧 N-1 完成 → 处理帧 N-1 结果
帧 N+1: infer_async(img_N+1)  → 等待帧 N 完成   → 处理帧 N 结果
```
**预期收益：** 帧率提升 30-50%。

---

#### Opt-2：SLERP 插值效率

**现状：** `Gimbal::q()` 使用 `while(true)` 循环不断 pop 队列丢弃数据。如果 IMU 帧率远高于图像帧率，会丢弃大量中间数据。

**优化方案：** 维护时间索引或使用二分查找定位数据对。

---

#### Opt-3：Planner 选板函数重复调用

**现状：** `choose_aim_selection()` 在 `solve_hit_target()` 的每次迭代中被调用，且在 `get_trajectory()` 的每步中也被调用。

**优化方案：** 如果目标运动状态未变，可缓存选板结果。但切板瞬间建议重新计算。

---

### 代码质量


#### Code-3：重复的配置加载逻辑

**位置：** `Planner::setup_yaw_solver()` 和 `setup_pitch_solver()`

**问题：** 两个函数有大段重复的配置加载代码（约 40 行），仅参数名不同。

**建议：** 提取为 `load_solver_config(const string& axis_name, ...)` 辅助函数。

---

#### Code-4：Decider 优先级映射硬编码

**位置：** `tasks/omniperception/decider.hpp:83-103`

**问题：** `mode1` 和 `mode2` 优先级映射直接写在头文件中，修改需要重新编译。

**建议：** 移至配置文件，运行时加载。

---

#### Code-5：exit(1) 硬退出

**位置：** `io/gimbal/gimbal.cpp:31`

**问题：** 串口打开失败时直接 `exit(1)`，不清理资源，不给上层处理机会。

```cpp
try {
  serial_.setPort(com_port);
  serial_.open();
} catch (const std::exception & e) {
  tools::logger()->error("[Gimbal] Failed to open serial: {}", e.what());
  exit(1);  // ← 硬退出，不清理
}
```

**建议：** 抛出异常或返回错误码，让应用层决定如何处理。

## 6.3 安全风险

#### Sec-1：WebDebugger 绑定 0.0.0.0

**位置：** `configs/sentry.yaml:134`

**问题：** `web_host: "0.0.0.0"` 使网页调试器对所有网络接口开放。在比赛现场可能被对手通过无线网络访问并修改参数。

**建议：**
- 生产环境绑定 `127.0.0.1`
- 或添加简单的访问密码/Token
- 或在比赛时禁用 WebDebugger

---

#### Sec-2：串口通信无加密/认证

**位置：** `io/gimbal/gimbal.cpp`

**问题：** `VisionToGimbal` 数据包仅靠帧头 0xA5 和 CRC16 校验，无身份认证或加密。

**评估：** 比赛环境中串口是有线连接，实际被干扰风险极低。但 CRC16 仅有 16 位，碰撞概率非零。

**建议：** 可接受现状。如需加强可考虑 CRC32 或添加序列号。

---

#### Sec-3：配置文件中的敏感信息

**位置：** `configs/*.yaml`

**问题：** 配置文件中包含相机内参、手眼标定参数等，这些是队伍的核心技术参数。

**建议：** `.gitignore` 中排除 `configs/` 目录，或使用模板文件 + 环境变量注入。

## 6.4 架构改进建议

#### Arch-1：缺少统一的错误处理机制

**现状：** 各模块错误处理不一致：
- `gimbal.cpp`: `exit(1)` 硬退出
- `camera.cpp`: 可能返回空图像
- `planner.cpp`: 抛 `std::runtime_error`
- `tracker.cpp`: 静默重置
- 其他: `logger()->warn` 记录后继续

**建议：** 定义统一的错误码体系：
```cpp
enum class VisionError {
  OK,
  CAMERA_INIT_FAILED,
  SERIAL_DISCONNECTED,
  MODEL_LOAD_FAILED,
  NO_VALID_TARGET,
  TRAJECTORY_UNSOLVABLE,
};
```

---

#### Arch-2：测试覆盖不足

**现状：** `tests/` 目录主要是集成测试和手动测试，缺少自动化单元测试框架。

**建议：** 为关键算法模块添加 Google Test 单元测试：
- `ExtendedKalmanFilter` — 预测/更新数学正确性
- `Trajectory` — 弹道解算精度
- `Planner` — 选板逻辑、开火决策
- `MathTools` — 角度归一化、四元数转换

---

#### Arch-3：ROS2 耦合度

**现状：** ROS2 依赖通过 CMake 条件编译控制，但 `io/ros2/` 代码直接引用 `rclcpp` 类型。如果 ROS2 接口变化需要修改多处代码。

**建议：** 定义更抽象的通信接口：
```cpp
class CommInterface {
  virtual void publish(const VisionTargetState &) = 0;
  virtual std::vector<int8_t> subscribe_enemy_status() = 0;
};
// ROS2Comm : CommInterface
// SocketComm : CommInterface (无 ROS2 时的备选)
```

---

#### Arch-4：配置管理碎片化

**现状：** 各模块独立加载 YAML 配置，相同参数可能在多处读取。修改配置需要知道哪些模块使用了该参数。

**建议：** 引入中心化配置管理器：
```cpp
class ConfigManager {
  static ConfigManager & instance();
  void load(const std::string & path);
  double get_double(const std::string & key);
  // ...
};
```

---

#### Arch-5：缺少 CI/CD 流程

**现状：** 无自动化构建和测试流程。

**建议：**
- 添加 GitHub Actions CI：编译 + 运行单元测试
- 添加 lint 检查（clang-tidy）
- 自动化文档生成
