# Awakening 可视化工程与网页调试器设计分析

## 1. 文档目的

这份文档面向想把 RoboMaster 视觉系统做得更工程化的开发者，重点分析本项目当前的可视化与网页调试器设计，并在此基础上给出适合纯 C++ 方案继续演进的改造建议。

本文不只描述“它现在怎么工作”，还会强调：

- 当前方案为什么好用
- 哪些设计对比赛工程非常实用
- 哪些实现已经开始接近瓶颈
- 如果你想做纯 C++ 的更工程化方案，应该怎样分层和演进

## 2. 当前系统中的“可视化工程”到底包含什么

这个项目里的可视化不是单一页面，而是一整套调试输出体系，主要包括四类输出：

1. 图像可视化
   在 C++ 主程序中把检测框、目标预测、弹道点、瞄准点、状态文本等直接画到图像上，再压缩成 JPEG 放入共享内存。

2. 时序曲线可视化
   把 yaw、pitch、目标角、云台角、控制速度、控制加速度、飞行时间等关键调试量写成 JSON，由网页轮询后绘制折线图。

3. 结构化状态日志
   把串口接收状态、目标状态等写成 JSON，对调试者来说相当于一个轻量状态总线快照。

4. ROS 2 三维可视化
   如果启用了 ROS 2，会额外发布装甲板 Marker、目标状态 Marker、TF，用 RViz 做三维空间层面的观察。

从工程角度看，这其实是一个“双层调试体系”：

- 二维快速调试层：网页 + 图像叠加 + 曲线
- 三维系统调试层：ROS 2 Marker + TF

这是本项目很值得借鉴的一点，因为比赛调试往往不只是看图像，更重要的是同时观察：

- 检测是否正确
- 目标状态估计是否稳定
- 控制量是否抖动
- 预测是否超前或滞后
- 坐标系是否一致

## 3. 当前架构总览

系统可以抽象成下面这条链路：

```text
C++ 主程序
  ├─ 采集实时图像 / 仿真图像 / 回放图像
  ├─ 执行检测、跟踪、控制
  ├─ 维护 AutoAimDebugCtx 调试上下文
  ├─ 绘制调试图
  ├─ 写共享内存 JPEG
  ├─ 写 /dev/shm JSON 数据
  └─ 可选发布 ROS2 Marker/TF

Python Flask 服务
  ├─ 读取共享内存中的 JPEG
  ├─ 提供 /video MJPEG 流
  ├─ 读取 /dev/shm/awakening_data.json
  ├─ 读取 /dev/shm/awakening_log.json
  └─ 提供网页前端

前端页面
  ├─ 展示视频流
  ├─ 定时拉取 JSON
  ├─ 用 Chart.js 绘制时序曲线
  └─ 用树形视图展示日志 JSON
```

这套架构的核心思想是：

- 主程序只负责“生产调试数据”
- 网页服务只负责“搬运和展示”
- 前后端之间用最简单的 IPC 手段打通

它没有引入消息队列、数据库、复杂 RPC，也没有把调试逻辑嵌进实时控制主循环里太深，因此上手门槛很低。

## 4. 当前可视化链路的详细拆解

## 4.1 C++ 侧调试上下文

当前项目用 `AutoAimDebugCtx` 作为调试数据聚合容器。它本质上是一个“松耦合快照仓库”，内部保存：

- 当前装甲板集合
- 当前目标状态
- 当前图像帧
- 当前 ROI
- 平均延迟
- 当前控制指令
- FSM 状态
- 云台姿态
- 子弹预测点
- 相机内参

这个设计的优点很明显：

- 业务逻辑不需要直接依赖网页模块
- 调试模块只读，不直接干扰主算法
- 便于集中绘图与集中导出

但它当前的实现方式比较偏“比赛快速落地”：

- 每个字段一把 `mutex`
- 访问粒度较细
- 图像帧直接拷贝
- 逻辑上属于共享对象，但缺少统一版本号或事务式快照

它适合先跑起来，但如果你要做纯 C++ 工程化升级，后面应该演进成：

- 单版本号快照结构
- 单写多读无锁或近无锁数据通道
- 热路径数据和冷路径数据分层

## 4.2 图像叠加层

当前图像叠加的内容非常完整，主要包括：

- 当前 ROI 框
- 原始检测到的装甲板
- 跟踪器推算出的装甲板投影
- 目标中心与角速度箭头
- 瞄准点与射击建议
- 控制速度箭头
- 子弹轨迹点
- 当前时间戳
- 平均延迟
- yaw / pitch 控制量文本
- FSM 状态文本
- 当前攻击目标编号
- 图像中心点

这套叠加层非常适合比赛现场，因为它不是“只画框”，而是把感知、估计、控制三层信息都映射到了图像平面里。

这意味着调试者能在一张图上同时回答以下问题：

- 检测到了什么
- 跟踪器认为目标在哪
- 目标旋转方向与速度是什么
- 预测瞄点在哪里
- 控制器输出了什么
- 系统建议是否开火

这类“多语义叠加图”是该项目最大的工程亮点之一。

## 4.3 共享内存图像通道

当前方案采用 POSIX 共享内存：

- 名称：`/awakening_frame`
- 实际路径：`/dev/shm/awakening_frame`
- 固定大小：2 MB
- 数据格式：`[4字节JPEG长度][JPEG字节流]`

优点：

- 实现极简
- 吞吐足够支撑调试图
- Python 读取非常容易
- 不需要引入 socket、序列化协议、第三方中间件

这对比赛工程很友好，因为“能快速看到图”比“协议是否优雅”更重要。

但它也有几个典型问题：

1. 没有版本号或帧序号
   读端无法判断拿到的是不是新帧。

2. 没有双缓冲或 seqlock
   写端先写长度再写 JPEG 内容，读端理论上可能读到写入中的中间状态。

3. 固定 2 MB 容量
   分辨率升高或 JPEG 质量提高后，可能直接超过上限。

4. JPEG 编码发生在 C++ 调试线程
   图像压缩是 CPU 热点，可能影响调试线程周期稳定性。

从工程视角，这是“够用但不够稳”的设计。

## 4.4 JSON 曲线数据通道

当前曲线数据采用文件落盘方式：

- `/dev/shm/awakening_data.json`
- 每次写入先写 `.tmp`
- 再 `rename()` 原子替换

当前保存的调试量主要有：

- `time`
- `yaw`
- `pitch`
- `target_yaw`
- `target_pitch`
- `gimbal_yaw`
- `gimbal_pitch`
- `control_v_yaw`
- `control_v_pitch`
- `control_a_yaw`
- `control_a_pitch`
- `fly_time`
- `target_v_yaw`

优点：

- 对前端特别友好
- 不需要自定义协议
- 改字段简单
- 临时排障时甚至可以直接 `cat /dev/shm/awakening_data.json`

缺点：

- 每次都是全量 JSON 序列化
- 每次都是整文件写入
- 前端也是全量拉取
- 没有 schema 版本控制
- 数据量变大后效率会迅速下降

也就是说，这是一种非常适合“少量关键曲线”的方案，不适合扩展成大型遥测系统。

## 4.5 结构化日志通道

当前还有一个 `/dev/shm/awakening_log.json`，主要写：

- 串口接收状态
- 哨兵状态
- 目标状态等调试信息

和曲线数据相比，这里更接近“最新快照”而不是“时间序列数据库”。

这类设计非常适合比赛现场，因为很多时候调试者关心的是：

- 当前云台姿态是多少
- 当前识别敌方颜色是什么
- 当前弹速是多少
- 当前目标状态机处于什么状态

用 JSON 快照比滚动日志更直观。

## 4.6 Python Flask 网页服务层

`web.py` 承担的职责很单纯：

- 把共享内存包装成 `/video`
- 把两个 JSON 文件包装成 `/data` 和 `/log`
- 渲染一个单页调试页面

这种设计有两个明显优点：

1. 非侵入
   不需要把 HTTP 服务器塞进 C++ 主程序。

2. 好维护
   Python 改页面、接口、调试逻辑非常快。

它的核心价值不在于“性能最好”，而在于“比赛现场改页面效率极高”。

## 4.7 前端页面层

前端页面当前由三块组成：

- 左上：视频流
- 右上：JSON 日志树
- 左下：多曲线主图
- 右下：独立子图

主要功能包括：

- 视频全屏
- 多曲线总览
- 单曲线拆分观察
- 每个子图独立设置 Y 轴范围
- JSON 树展开查看

这对调 PID、调延迟补偿、调目标速度估计非常有帮助。

其思路本质上是：

- 总图看耦合关系
- 单图看局部波动
- JSON 看状态上下文
- 图像看空间语义

这四种视角组合起来，调试体验会比单纯打印日志高很多。

## 4.8 ROS 2 可视化层

如果编译时启用了 ROS 2，系统还会发布：

- 装甲板 Marker
- 跟踪目标 Marker
- 目标线速度箭头
- 目标角速度箭头
- 机器人 TF

这层的意义是网页无法替代的，因为网页更偏二维，而 ROS 2 / RViz 更适合检查：

- 坐标变换是否正确
- 目标在三维空间中的位置是否合理
- 跟踪器输出姿态是否跳变
- 相机系、云台系、odom 系之间是否一致

这是一种非常典型的 RoboMaster 工程组合：

- 网页看人机交互
- RViz 看几何关系

## 5. 当前设计值得保留的工程思想

## 5.1 调试链路与算法链路解耦

当前项目没有让网页调试器直接参与算法决策，这非常重要。

好的实时系统中，调试模块应该是旁路观察者，而不是主决策链的一部分。这个项目做到了：

- 算法主链还能独立运行
- 调试可开可关
- 关闭 debug 后，大部分网页相关逻辑不会参与热路径

## 5.2 可视化信息是“分层”的

该项目没有把所有信息都塞进一张图里，而是自然形成了分层：

- 图像叠加看感知几何
- 曲线看时序行为
- JSON 看状态快照
- ROS 2 看三维空间

这正是成熟调试体系该有的样子。

## 5.3 输出内容围绕“命中率问题”组织

它不是为了炫 UI，而是围绕真实比赛问题构建的：

- 为什么没识别出来
- 为什么跟踪抖
- 为什么预测过冲
- 为什么云台不打
- 为什么明明看见了却不开火

这说明它的调试字段是围绕业务问题设计的，而不是为了“把能输出的全输出”。

## 5.4 IPC 手段非常务实

共享内存加 JSON 文件的组合虽然不高级，但有几个巨大优点：

- 依赖少
- 出问题容易查
- 跨语言简单
- 部署成本低

对于比赛系统，这其实是非常正确的取舍。

## 6. 当前方案存在的主要工程问题

下面这些问题不是“不能用”，而是“如果你要做长期可维护的纯 C++ 工程版，应该重点改掉”。

## 6.1 图像通道缺少一致性保护

当前共享内存图像通道没有：

- 帧序号
- 时间戳
- 版本号
- 双缓冲
- 写入完成标记

这会导致读端拿到的帧不一定具备严格一致性。

虽然当前通过 JPEG 头判断能规避一部分坏帧，但这不是真正的同步协议。

## 6.2 JSON 方式在规模扩大后会成为瓶颈

当前每次更新都要：

- 序列化整个 JSON
- 写临时文件
- 重命名替换
- 前端整包拉取

如果未来你想加入：

- 更多控制量
- 每装甲板的历史轨迹
- 多目标数据
- 调试录像索引
- 延迟分解数据

那么这个机制会迅速变重。

## 6.3 调试图生产仍然离热路径太近

当前调试图生成包含：

- 图像 clone
- 颜色空间转换
- 几何重投影
- 文本绘制
- 子弹轨迹绘制
- JPEG 压缩

这些都在调试频率任务里执行。

虽然已经不在核心求解线程上，但它仍然运行在主程序内部，与实时任务共享 CPU 资源。

对于高帧率平台，这会明显消耗算力预算。

## 6.4 DebugCtx 的并发模型较粗糙

当前 `AutoAimDebugCtx` 每个字段一把锁，优点是简单，但问题是：

- 状态不是同一时刻的强一致快照
- 读者可能拿到“跨帧混合状态”
- 锁粒度太细，不利于统一版本管理

如果你的系统越来越复杂，这会让调试结果本身变得不完全可信。

## 6.5 前端轮询存在重复与冗余

当前前端实际上存在两套数据拉取节奏：

- `main.js` 中每 200 ms 拉一次图表和 JSON
- `chart_logic.js` 中又启动了 100 Hz 的图表轮询

这意味着图表接口有重复拉取问题，会造成：

- 无意义的 HTTP 请求
- 前端与 Flask 额外开销
- 曲线刷新节奏不稳定

这是一个很典型的“快速迭代后遗留”的前端工程问题。

## 6.6 Flask 只是展示层，没有数据缓存和节流

当前 Flask 每次请求都直接：

- 读共享内存
- 打开 JSON 文件
- 反序列化 JSON

这个设计简单，但缺少：

- 缓存层
- 更新时间戳
- 请求合并
- 订阅推送

在单用户时问题不大，多客户端观察时会开始放大成本。

## 6.7 调试数据没有 schema 与版本管理

当前 `/data` 和 `/log` 基本是“约定字段名”。

这种方式前期很灵活，但中后期会出现：

- 字段新增后前端兼容性差
- 历史工具无法复用
- 多模块调试字段难统一

如果你准备把自己的系统做得更正规，建议尽早引入“调试数据 schema”概念。

## 7. 如果你要做纯 C++ 工程化升级，建议的目标架构

如果你的目标是把现有思路升级成更工程化、更纯 C++ 的方案，我建议不要直接“一把梭全重写”，而是保留它最有价值的思想，再替换底层通道和数据组织方式。

建议目标架构如下：

```text
算法层
  ├─ Detector / Tracker / Controller
  └─ DebugPublisher

调试数据总线层
  ├─ ImageChannel
  ├─ TelemetryChannel
  ├─ EventChannel
  └─ ConfigSnapshotChannel

可视化服务层（推荐仍与算法进程解耦）
  ├─ C++ HTTP/WebSocket 服务
  ├─ 调试记录器
  ├─ 回放管理器
  └─ 前端静态资源服务

前端展示层
  ├─ 视频视图
  ├─ 曲线视图
  ├─ 目标列表与状态树
  ├─ 延迟分解页
  └─ 参数调优页
```

这套结构和当前项目相比，最大的变化有三点：

1. 从“文件/共享内存输出”升级为“统一调试数据总线”
2. 从“网页是附属工具”升级为“可视化服务是独立模块”
3. 从“字段集合”升级为“有 schema 的数据模型”

## 8. 推荐你重点改造的 10 个方向

## 8.1 建立统一的 DebugPublisher 接口

不要让业务模块直接知道：

- JSON 文件怎么写
- 共享内存怎么写
- HTTP 怎么提供

建议统一收口成接口，例如：

```cpp
class DebugPublisher {
public:
    virtual void publishImage(const DebugImageFrame& frame) = 0;
    virtual void publishTelemetry(const TelemetrySnapshot& snapshot) = 0;
    virtual void publishEvent(const DebugEvent& event) = 0;
    virtual ~DebugPublisher() = default;
};
```

这样做的好处是：

- 算法层不关心展示技术
- 后面换成 WebSocket、共享内存、录制文件都更方便
- 单元测试容易做

## 8.2 图像通道改成“双缓冲 + 帧头协议”

建议图像共享通道至少加入下面这些字段：

- magic
- version
- frame_id
- timestamp_ns
- codec
- payload_size
- width
- height
- status / ready flag

再配合：

- 双缓冲
- seqlock
- 原子切换索引

这样读端就能明确知道：

- 当前拿到的是哪一帧
- 数据有没有写完
- 分辨率是不是变化了

## 8.3 曲线数据改成“增量推送”而不是“全量 JSON”

如果继续走网页路线，推荐：

- 后端维护环形缓冲区
- 前端通过 WebSocket 订阅增量点
- 页面按 `topic` 或 `series_id` 追加

而不是每次把整个 `time + 所有曲线` 全量重发。

这会立刻改善：

- 刷新负担
- 延迟
- 前后端 CPU 占用
- 多图扩展能力

## 8.4 结构化日志与时序遥测分开建模

当前项目里 `/log` 和 `/data` 已经有这个雏形，建议你继续强化成两类数据：

1. Telemetry
   高频、数值型、时间序列

2. StateSnapshot / Event
   中低频、结构化、状态型

不要混在一个 JSON 里，否则后期会越来越乱。

## 8.5 图像渲染线程彻底旁路化

当前调试图绘制已经不在最热的检测/控制代码里，但我仍建议继续旁路化：

- 算法线程只发布轻量 debug primitive
- 独立渲染线程消费 primitive 并绘图

例如 primitive 可以是：

- lines
- circles
- polygons
- text
- arrows
- 3D projected armor boxes

这样渲染线程可以：

- 自己决定降帧
- 自己决定压缩质量
- 自己决定是否跳帧

算法线程则保持干净。

## 8.6 给调试数据增加时间戳与来源阶段

推荐每一条调试数据都至少带：

- source timestamp
- publish timestamp
- frame id
- stage name

例如：

- detector_output
- tracker_output
- aimer_output
- serial_rx
- serial_tx

这样你就能直接在网页里做：

- 端到端延迟拆解
- 各阶段时延柱状图
- 帧丢失分析
- 异步错配分析

这是非常有价值的工程能力。

## 8.7 建立“可录制可回放”的调试总线

当前项目已经有录制与回放能力，但更偏原始输入流。

如果你要做更强的工程版，建议把下列内容都支持录制：

- 原始图像
- 检测结果
- 跟踪状态
- 控制输出
- 串口收发
- 网页调试遥测
- 参数快照

这样你的回放就不只是“重跑视频”，而是完整复现一次系统行为。

## 8.8 前端改成“页面分域”而不是单页堆叠

当前页面很实用，但随着功能增加会越来越拥挤。

更工程化的前端建议分成几页：

- 实时图像页
- 控制曲线页
- 目标状态页
- 延迟分析页
- 回放分析页
- 参数管理页

这会让整个系统从“调试面板”进化成“调试工作台”。

## 8.9 把 ROS 2 可视化和网页可视化视为两个正交系统

不要想着二选一，正确做法是：

- 网页负责高频人机调参
- ROS 2 负责空间关系与系统集成调试

如果你做纯 C++ 方案，也建议保留这个分层思路。

## 8.10 建立调试字段规范

建议统一命名规则，例如：

- `gimbal.yaw_deg`
- `gimbal.pitch_deg`
- `target.vyaw_deg_s`
- `control.yaw_cmd_deg`
- `latency.detector_ms`
- `latency.total_ms`

并为每个字段规定：

- 单位
- 更新频率
- 是否可回放
- 是否关键指标

这会让整个工程长期维护成本下降很多。

## 9. 针对“纯 C++ 实现”的推荐路线

你说你现在是纯 C++ 实现，这很好，因为如果设计得当，纯 C++ 完全可以把当前这套方案做得更稳定、更可控。

我建议的演进路线是：

### 第一阶段：保留网页，先把后端 IPC 和数据组织做好

目标：

- 保留前端网页
- 先把共享内存、JSON、并发模型正规化

优先改：

- 图像双缓冲
- DebugCtx 快照化
- 增量遥测
- 统一 DebugPublisher

### 第二阶段：C++ 内建轻量服务层

目标：

- 用 C++ 提供 HTTP + WebSocket
- 去掉 Python Flask 依赖

可选方案：

- `Boost.Beast`
- `uWebSockets`
- `Crow`
- `oatpp`

这样你就能做到真正的纯 C++ 可视化后端。

### 第三阶段：形成完整调试平台

目标：

- 实时调试
- 参数下发
- 回放分析
- 延迟诊断
- 多车多节点观测

到了这一步，你的系统就不是“能看图的视觉程序”，而是完整的工程平台。

## 10. 我对这个项目设计的总体评价

从 RoboMaster 比赛工程角度，这个项目的可视化体系是很实用的，尤其有以下优点：

- 把图像、曲线、日志、ROS 2 三种观察方式结合起来了
- 调试字段围绕命中率问题组织，方向很对
- 调试模块对主链路侵入不深
- 共享内存和 JSON 的选择很朴素，但落地成本低

它的问题主要不在“方向错了”，而在于这是一套典型的“比赛工程已经很好用，但离长期平台化还有一步”的实现。

如果你要在自己的纯 C++ 方案里继续优化，我建议：

- 保留它的分层思路
- 保留它的多视角调试哲学
- 改掉它的 IPC 协议、并发快照和前后端数据组织方式

换句话说：

- 思路值得继承
- 底层实现值得升级

## 11. 最推荐你立刻落地的改动清单

如果你想最短时间做出“明显比当前更工程化”的版本，我建议优先做下面 8 件事：

1. 把调试输出统一收口到 `DebugPublisher`。
2. 给共享内存图像协议加帧头、帧号、双缓冲。
3. 把 JSON 全量轮询改成 WebSocket 增量遥测。
4. 把 `AutoAimDebugCtx` 改成单快照结构，而不是多把锁拼装。
5. 把图像绘制与 JPEG 编码放进独立渲染线程。
6. 给每个调试字段加入单位、来源阶段、时间戳。
7. 把页面拆成实时图像页、曲线页、状态页、回放页。
8. 保留 ROS 2 Marker 体系，作为三维空间调试层。

## 12. 结论

这个项目的网页调试器并不复杂，但设计方向是对的。它最有价值的地方，不是 Flask 或 Chart.js，而是它已经形成了一套围绕自动瞄准问题的“可观测性体系”。

如果你要做自己的纯 C++ 工程化版本，最合理的路径不是推翻重来，而是：

- 继承它的调试分层思维
- 重做它的数据总线与服务层
- 让调试输出成为正式架构的一部分

这样做出来的系统，才会既有比赛环境下的实用性，又有长期维护和持续扩展的工程质量。
