# 自瞄模块解析

这份文档专门聚焦 `tasks/auto_aim` 目录本身，不再只做“模块简介”，而是按当前 `sp_vision25` 工程的真实实现，把自瞄主模块拆成一份可直接对照源码的算法分析文档。

它重点回答四件事：

1. `tasks/auto_aim` 内部到底包含哪些算法层。
2. 这些层之间传递的核心数据是什么。
3. 前哨站与普通装甲板共用了哪些逻辑，又在哪些地方做了特化。
4. 当前项目里“模块能力”和“入口程序真实接法”分别是什么。

建议配合下面几份文档一起看：

1. [自瞄代码阅读指南](./自瞄代码阅读指南.md)
   适合按源码阅读顺序看。
2. [autoaim_analysis](./autoaim_analysis)
   适合看更长篇的方案梳理和传统/MPC 对照。
3. [outpost_analysis.md](./outpost_analysis.md)
   适合做前哨专项验收与实车排障。

## 1. 模块边界与在工程中的位置

`tasks/auto_aim` 的职责不是“把整个程序跑起来”，而是负责自动瞄准主算法本身。

它主要完成：

1. 检测结果统一表示
2. 装甲板空间解算
3. 目标状态估计与跟踪
4. 瞄准点选择
5. 开火门控或连续控制量生成

它不负责：

1. 相机读图
2. 串口/云台通信
3. 主线程与子线程调度
4. Web 调试页面管理

这些调度逻辑在 `src/*.cpp`。

所以读 `tasks/auto_aim` 时，始终要分清两层：

```text
入口程序层：决定当前到底跑 Aimer 还是 Planner，是否真的调用 Shooter
算法模块层：Detector/YOLO -> Solver -> Tracker -> Aimer/Shooter 或 Planner
```

## 2. 当前项目中的两条主算法链

### 2.1 传统链

```text
Detector / YOLO
  -> Armor
  -> Solver
  -> Tracker
  -> Aimer
  -> Shooter
  -> io::Command
```

注意这里的 `Shooter` 是模块能力，不等于每个入口都用了它。

当前工程里：

1. `src/standard.cpp`
   只走到 `Aimer -> cboard.send(command)`，没有真正调用 `shooter.shoot()`。
2. `src/mt_standard.cpp`
   才更接近完整的 `Aimer + Shooter` 传统链。
3. `src/uav.cpp`、`src/sentry*.cpp`
   也有实际调用 `Shooter::shoot()` 的实现。

### 2.2 MPC 链

```text
Detector / YOLO
  -> Armor
  -> Solver
  -> Tracker
  -> Planner
  -> Plan
```

这里 `Planner` 不是 `Aimer` 的简单后处理，而是一套并行的控制路线。

它直接输出：

1. `yaw`
2. `pitch`
3. `yaw_vel`
4. `pitch_vel`
5. `yaw_acc`
6. `pitch_acc`
7. `fire`

当前工程里：

1. `src/standard_mpc.cpp`
   使用主线程感知、`plan_thread` 规划。
2. `src/auto_aim_debug_mpc.cpp`
   直接在主循环内做 `detect -> track -> plan -> send`，并叠加调试输出。

## 3. 模块级总数据流

可以把当前 `tasks/auto_aim` 理解成下面五层：

```text
检测层:
  Detector / YOLO
    -> Armor

解算层:
  Solver
    -> Armor(补全3D信息)

跟踪层:
  Tracker
    -> Target

传统火控层:
  Aimer -> io::Command
  Shooter -> bool shoot

MPC 火控层:
  Planner -> Plan
```

这也是为什么当前文档要按“数据结构 -> 解算 -> 跟踪 -> 火控”来讲，因为模块之间真正耦合的核心就是：

1. `Armor`
2. `Target`
3. `io::Command`
4. `Plan`

## 4. 核心数据结构

### 4.1 `Armor`：检测层和算法层之间的统一中间表示

定义在 `tasks/auto_aim/armor.hpp/.cpp`。

它同时承载两类信息。

第一类是 2D 检测结果：

1. 四个角点 `points`
2. 中心 `center`
3. 包围框 `box`
4. 颜色 `color`
5. 类别 `name`
6. 类型 `type`
7. 置信度 `confidence`

第二类是经过 `Solver` 补全后的 3D 信息：

1. `xyz_in_gimbal`
2. `xyz_in_world`
3. `ypr_in_gimbal`
4. `ypr_in_world`
5. `ypd_in_world`

所以可以把它理解成：

```text
Armor = 检测结果 + 空间解算结果
```

当前项目里，前哨并不是一个“整体目标类型”，而是一块类别为 `ArmorName::outpost` 的装甲板。

这意味着：

1. 检测层只需要识别“这块板是不是 outpost”。
2. 真正把它建模成三板旋转目标，是后面的 `Target + Tracker` 在做。

### 4.2 `Target`：跟踪层对目标的统一状态表示

定义在 `tasks/auto_aim/target.hpp/.cpp`。

它是 `Tracker` 交给 `Aimer/Planner` 的统一对象，内部是一套 11 维 EKF 状态：

```text
x = [cx, vcx, cy, vcy, cz, vcz, yaw, vyaw, r, l, h]
```

含义如下：

1. `cx, cy, cz`
   目标旋转中心
2. `vcx, vcy, vcz`
   目标中心速度
3. `yaw`
   参考装甲板相位
4. `vyaw`
   角速度
5. `r`
   基础旋转半径
6. `l`
   四板目标的长短半径差
7. `h`
   四板目标的高低差

要特别注意：

1. 普通四板目标真的会用到 `r/l/h` 去区分不同板位。
2. 前哨目标虽然复用了同一个状态向量，但板间高度主要由 `outpost_armor_z_offsets` 表示，而不是依赖 `h`。

### 4.3 `io::Command` 与 `Plan`

两者不要混淆。

`io::Command` 是传统链输出：

1. `control`
2. `shoot`
3. `yaw`
4. `pitch`

`Plan` 是 MPC 链输出：

1. `control`
2. `fire`
3. `target_yaw`
4. `target_pitch`
5. `yaw`
6. `pitch`
7. `yaw_vel`
8. `pitch_vel`
9. `yaw_acc`
10. `pitch_acc`

一句话概括：

```text
Aimer 输出点命令
Planner 输出轨迹中点对应的连续控制状态
```

## 5. 检测层：YOLO 与传统检测在当前项目中的关系

### 5.1 统一入口：`yolo.cpp`

`tasks/auto_aim/yolo.cpp` 只是一个分发器，会根据配置里的 `yolo_name` 选择：

1. `YOLOV5`
2. `YOLOV8`
3. `YOLO11`

当前主配置常用的是 `YOLOV5`，所以真正值得优先细读的是 `tasks/auto_aim/yolos/yolov5.cpp`。

### 5.2 `YOLOV5` 的当前流程

`YOLOV5::detect()` 的主流程可以概括成：

```text
原图
  -> 可选 ROI 裁图
  -> 等比例缩放到 640x640
  -> OpenVINO 推理
  -> parse 输出
  -> NMS
  -> Armor 列表
```

其中 `parse()` 会做几件关键事：

1. 从网络输出中取出四角点
2. 取出颜色类别和数字类别
3. 恢复到原图尺度
4. 通过 NMS 去重
5. 构造 `Armor`
6. 过滤无效类别和类别-尺寸不一致结果

### 5.3 `use_traditional` 的实际含义

当前工程里 `YOLOV5` 并不是纯神经网络闭环。

当 `use_traditional=true` 时，YOLO 产生的装甲板还会交给传统检测器做一次二次矫正：

```text
YOLO 给出粗角点
  -> detector_.detect(*it, bgr_img)
  -> 对角点做传统方法修正
```

所以当前项目更准确的理解方式是：

```text
YOLO 负责目标发现和初始定位
传统检测负责局部角点修正
```

### 5.4 前哨在检测层的真实位置

前哨在检测层并没有单独的“前哨模型”。

它只是：

1. 类别为 `ArmorName::outpost`
2. 类型为 `ArmorType::small`

因此前哨专项能力并不主要体现在检测层，而是体现在：

1. `Target`
2. `Tracker`
3. `Planner`

## 6. 解算层：`Solver`

### 6.1 模块职责

`tasks/auto_aim/solver.cpp` 负责把装甲板四角点变成后续算法能直接使用的三维观测。

它主要完成：

1. 根据大小选择 3D 模板点
2. `solvePnP(IPPE)`
3. `camera -> gimbal -> world` 坐标变换
4. 计算装甲板姿态 `ypr`
5. 计算观测线方向 `ypd`
6. 做一次 yaw 优化

### 6.2 两套模板点

代码里根据装甲板类型选择：

1. `BIG_ARMOR_POINTS`
2. `SMALL_ARMOR_POINTS`

这一步本质上是在说：

```text
解算层默认认为：装甲板是一个已知尺寸的平面矩形
```

因此检测层给出的 `type` 是否可靠，会直接影响 PnP 结果。

### 6.3 空间变换链

`solve()` 内部的核心链路是：

```text
像素角点
  -> solvePnP(IPPE)
  -> xyz_in_camera
  -> xyz_in_gimbal
  -> xyz_in_world
```

同时还会把姿态矩阵一路转换成：

1. `ypr_in_gimbal`
2. `ypr_in_world`
3. `ypd_in_world`

其中 `ypd` 是后面跟踪层直接使用的重要观测量。

### 6.4 yaw 优化为什么存在

`solvePnP` 对平面目标的 yaw 往往不够稳定，特别是在斜视、远距离和角点抖动时。

当前工程会对非平衡大装甲板再做一次 `optimize_yaw()`：

1. 以当前云台 yaw 为中心，做一段范围搜索
2. 对每个候选 yaw 做重投影
3. 取重投影误差最小的 yaw 作为修正结果

平衡大装甲板不做这一步，因为当前的 pitch 假设对它不一定成立。

### 6.5 前哨在重投影里的特殊点

`reproject_armor()` 对 pitch 做了一个固定假设：

1. 普通板默认 `pitch = +15°`
2. 前哨默认 `pitch = -15°`

这点很重要，因为：

1. `Tracker` 的前哨匹配依赖重投影误差
2. 如果这个几何假设偏差很大，前哨匹配评分就会被系统性拉坏

所以当前项目里，前哨的“匹配对不对”并不只是 `Tracker` 的问题，`Solver` 的重投影假设也直接参与了这个结果。

## 7. 跟踪层：`Target + Tracker` 才是当前前哨方案的核心

### 7.1 `Tracker` 的两件大事

`Tracker` 做两类工作：

1. 状态机管理
2. `Armor -> Target` 的关联与更新

从主循环角度看，它做的是：

```text
当前帧 Armor 列表
  -> 预测已有目标
  -> 做观测关联
  -> 更新 EKF
  -> 输出 Target
```

### 7.2 `Tracker` 的状态机

当前状态机包括：

1. `lost`
2. `detecting`
3. `tracking`
4. `temp_lost`
5. `switching`

基本逻辑是：

1. `lost`
   找到目标后进入 `detecting`
2. `detecting`
   连续检测达到 `min_detect_count_` 后进入 `tracking`
3. `tracking`
   当前帧没找到就进入 `temp_lost`
4. `temp_lost`
   短时丢失时继续保留目标，超过阈值才回 `lost`
5. `switching`
   主要服务全向感知切目标

其中前哨的 `temp_lost` 阈值更大，因为它更容易出现板间空窗和短时遮挡。

### 7.3 `set_target()`：不同目标的初始化方式不同

`Tracker::set_target()` 会按装甲板类型选择不同目标模型。

当前主要分成四类：

1. 平衡步兵
   用 2 板模型
2. 前哨
   用 3 板模型，半径来自 `outpost_radius`
3. 基地
   也是 3 板模型
4. 普通装甲板
   用 4 板模型

其中前哨初始化时最关键的是：

1. `armor_num = 3`
2. `outpost_radius_`
3. `outpost_armor_z_offsets_`
4. `outpost_fixed_center_rotation_model_`
5. `outpost_spin_speed_lock_`

### 7.4 `Target` 的预测模型

`Target::predict()` 现在有两种模式。

第一种是通用常速度/常角速度模型：

1. 中心位置按速度推进
2. 相位按角速度推进
3. `Q` 按 PWNA 模型构造

第二种是前哨常用的固定中心旋转模型：

1. 强制平移速度项趋近于 0
2. 主要只保留相位 `yaw` 和角速度 `vyaw` 的演化
3. 中心位置只做很小过程噪声漂移

这反映了当前项目对前哨的一个核心假设：

```text
前哨的主运动是绕固定中心旋转，而不是整体平移
```

### 7.5 前哨角速度锁

当目标已经收敛、且是前哨、且角速度绝对值大于阈值时，`Target::predict()` 会把角速度锁到 `spin_speed_lock_`。

它的作用是：

1. 减少角速度在短时噪声下的漂移
2. 让后续板位预测更稳定
3. 提高板间空窗阶段的可持续预测能力

这也是前哨专项策略的一部分。

### 7.6 `Target::update()`：普通目标如何关联

对于普通目标，`Target::update()` 会：

1. 先展开当前状态下的理论装甲板列表 `armor_xyza_list()`
2. 取距离更近的前几个候选板
3. 比较观测 yaw 与 LOS yaw 误差
4. 选择最佳匹配板号
5. 再做 EKF 更新

观测量是：

```text
z = [yaw_los, pitch_los, distance, armor_yaw]
```

对应的更新函数通过：

1. `h_armor_xyz()`
2. `xyz2ypd()`
3. `h_jacobian()`

把状态空间映射到观测空间。

### 7.7 `r/l/h` 与不同板位的几何含义

`Target::h_armor_xyz()` 里有一个很关键的分支：

1. 默认板位使用半径 `r`
2. 四板目标中的另外两块板可以使用 `r + l`
3. 高度也可以对某些板位叠加 `h`

也就是说，四板目标不是简单“等半径、等高度”模型，而是允许：

1. 长短轴不同
2. 板间高度不同

### 7.8 前哨为什么单独走 `select_best_outpost_match()`

当前前哨不会直接复用普通目标的更新逻辑，而是单独走 `Tracker::update_target()` 里的前哨分支。

它会调用 `select_best_outpost_match()`，把每一块观测板与每一个：

1. 理论板号 `id`
2. 物理板偏移 `offset`

组合起来评分。

评分项包括：

1. 重投影误差
2. LOS yaw 误差
3. pitch 误差
4. 距离误差
5. 装甲板自身 yaw 误差
6. 平面位置误差 `xy_error`
7. 高度误差 `z_error`
8. 连续性惩罚

这个实现说明当前前哨问题的本质不是“看到了没”，而是：

```text
当前这块观测板到底对应三板模型中的哪一块，以及物理板号映射是否连续
```

### 7.9 `id + offset` 联合匹配与物理板号重映射

前哨专项里最重要的一件事，就是区分：

1. 当前局部理论板号 `id`
2. 当前物理板号映射偏移 `offset`

`Target::set_armor_id_offset()` 会在偏移变化时，保持当前参考板高度连续，避免一改映射就把 `z` 直接跳坏。

这一步非常关键，因为前哨的三块板不是同高的。

如果没有这层“局部板号 -> 物理板号”映射，后面的：

1. 板位高度
2. 开火高度补偿
3. 板间切换连续性

都会出现系统性错位。

### 7.10 前哨匹配何时判失败

`accept_outpost_match()` 不是只看是否找到候选，而是还要求：

1. 匹配分数有限
2. 重投影误差不过大
3. `xy_error` 不过大
4. `z_error` 不过大
5. 总分不过阈值

也就是说，前哨跟踪现在走的是：

```text
宁可短时拒绝更新，也不把错板强行喂给 EKF
```

这对实车前哨稳定性是对的，因为前哨一旦错板，后面的控制层通常会被连锁带偏。

### 7.11 收敛与发散判定

当前 `Target` 还有两层保护：

1. `diverged()`
   检查 `r/l/h` 是否超出合理范围
2. `convergened()`
   普通目标更新次数超过 3 次可认为收敛
   前哨需要超过 10 次才认为收敛

再加上 `Tracker` 自己的 NIS 窗口统计，当前工程实际上在做三层防守：

1. 参数边界防守
2. 收敛次数防守
3. 统计一致性防守

## 8. 传统火控层：`Aimer + Shooter`

### 8.1 `Aimer` 的工作目标

`Aimer` 不是简单从 `Target` 里拿一个 yaw/pitch。

它当前实际在做：

1. 按延迟把目标预测到未来
2. 选择当前应击打的装甲板
3. 用弹道模型迭代命中时间
4. 输出 `io::Command(yaw, pitch)`

### 8.2 `Aimer::aim()` 的整体流程

可以概括成：

```text
Target
  -> 根据角速度选高/低速 delay
  -> 预测到未来决策时刻
  -> choose_aim_point()
  -> 弹道求解
  -> 固定点迭代飞行时间
  -> 输出 yaw / pitch
```

其中飞行时间不是只解一次，而是会迭代：

1. 先按当前目标位置求第一次飞行时间
2. 再把目标预测到命中时刻
3. 重新选板、重新算弹道
4. 直到飞行时间收敛或达到迭代上限

这比“只按当前时刻直接打一枪”的方法更接近真实命中逻辑。

### 8.3 `choose_aim_point()` 的两套分支

`Aimer` 的选板逻辑分成两大类。

第一类是非小陀螺：

1. 可见窗口固定为 `60°`
2. 若只有一块板可打，直接选它
3. 若多块板可打，则用 `lock_id_` 做锁板，减少来回切板

第二类是小陀螺/前哨：

1. 当角速度大于阈值，或目标本身就是前哨，就走旋转窗口分支
2. 在 `coming_angle` 内找“正在进入窗口”的板
3. 如果没有满足条件的板，再退回最近板

### 8.4 `Aimer` 当前前哨策略的一个重要现实

虽然 `Aimer` 支持前哨，但它现在对前哨的窗口仍然是硬编码：

1. `coming_angle = 70°`
2. `leaving_angle = 30°`

这和 `Planner` 已经参数化、并增加了命中相位门的前哨策略相比，仍然更朴素。

所以要明确：

```text
Aimer 可以打前哨
但当前项目里更完整的前哨策略在 Planner
```

### 8.5 `Shooter` 的职责

`Shooter` 并不负责算瞄准角，只负责“当前这一拍能不能开火”。

它当前看三件事：

1. 当前 `command` 是否有效
2. 当前云台位置是否接近上一帧命令
3. `aimer.debug_aim_point` 是否有效

同时还会比较：

1. 当前命令与上一帧命令的跳变量
2. 目标距离对应的近距离/远距离容差

它的核心思想是：

```text
如果这一帧命令突变太大，或者云台还没跟上上一帧命令，就先别开火
```

### 8.6 文档里建议区分的一个误区

很多时候看到模块里有 `Shooter`，容易误以为“传统入口都自带开火门控”。

但当前项目并不是这样。

例如：

1. `standard.cpp`
   实例化了 `Shooter`，但没调用
2. `mt_standard.cpp`
   才通过 `CommandGener` 串起完整的 `Aimer + Shooter`

所以排查“为什么没开火”“为什么过早开火”时，一定要先确认当前跑的是哪个入口。

## 9. MPC 火控层：`Planner`

### 9.1 `Planner` 的定位

`Planner` 是当前项目里更完整的连续控制方案。

它不是做“选好一个板以后给出一个角度”，而是：

1. 预测目标未来状态
2. 选择命中时刻要打的板
3. 构造未来参考轨迹
4. 分别对 yaw/pitch 求解 TinyMPC
5. 输出一组带速度、加速度的控制状态

### 9.2 `plan(std::optional<Target>)` 与 `plan(Target)` 的分工

这两个接口要分开理解。

第一层 `plan(std::optional<Target>, bullet_speed)` 负责：

1. 处理空目标
2. 根据目标类型选控制延迟
3. 先把目标预测到未来决策时刻

第二层 `plan(Target, bullet_speed)` 负责：

1. 命中时刻固定点迭代
2. 轨迹构造
3. MPC 求解
4. 开火判定

### 9.3 延迟补偿

`Planner::resolve_delay_time()` 当前是分支处理的：

1. 前哨若配置了 `outpost_delay_time`，优先用它
2. 否则按角速度与 `decision_speed` 比较，选择高低速延迟

这说明当前项目已经把“前哨控制延迟”和“普通小陀螺控制延迟”拆开了。

### 9.4 `choose_aim_selection()`：MPC 的选板逻辑

`Planner` 的选板逻辑和 `Aimer` 同源，但更完整。

它会先展开：

1. 目标中心 yaw
2. 所有理论装甲板的 `delta_angle`

然后分三种情况：

1. 目标还没真实跳板
   直接使用当前观测板，避免初始相位被强行切坏
2. 非小陀螺
   在 `60°` 可见窗口内锁板
3. 小陀螺/前哨
   在 `coming/leaving` 窗口内优先选“正在进入射击窗口”的板

这一版比传统 `Aimer` 更强调：

```text
命中时刻打的是哪块板
而不是当前视觉上最近的是哪块板
```

### 9.5 命中时刻固定点迭代

`Planner` 里最关键的一步是 `solve_hit_target()`。

它做的是：

```text
选板
  -> 计算弹道飞行时间
  -> 把目标预测到命中时刻
  -> 再次选板
  -> 再次计算飞行时间
```

直到满足：

1. 飞行时间收敛
2. 板号不再变化

这个设计对前哨尤其关键，因为前哨在飞行时间内很可能已经转过明显角度。

如果只按“当前板”直接生成整段参考轨迹，后面的 MPC 很可能从一开始就跟错板。

### 9.6 `resolve_aim_xyz()`：前哨开火高度补偿

`Planner` 当前支持 `outpost_fire_z_compensation`。

它会在已经选好板之后，再根据：

1. 当前是否为前哨
2. 当前板对应的物理板号

对 `z` 方向做补偿。

也就是说，当前前哨不仅有“跟踪层板位高度”，还有“火控层额外击打高度补偿”。

这通常用于修正：

1. 板间真实高度误差
2. 弹道落点和装甲板视觉中心不完全重合的问题

### 9.7 `get_trajectory()`：参考轨迹如何构造

`Planner` 在拿到命中时刻目标后，会围绕当前时刻前后展开一段预测轨迹。

轨迹每一列包含：

1. 相对 yaw
2. yaw 速度
3. pitch
4. pitch 速度

其中有两个实现细节很重要：

1. `yaw0` 作为参考中心，轨迹里存的是相对 yaw，方便 MPC 解小角度跟踪问题
2. 对异常大的 `yaw_acc` 做轻量抑制，避免切板瞬间参考速度尖峰把 MPC 拽偏

### 9.8 双 TinyMPC 结构

当前 `Planner` 不是一个联合 4 维控制器，而是拆成两套 2 状态、1 输入的 MPC：

1. yaw MPC
2. pitch MPC

状态形式一致：

```text
x = [angle, angle_vel]
u = [angle_acc]
```

好处是：

1. 调参简单
2. 计算量小
3. 可以分别限制 yaw/pitch 的最大加速度

### 9.9 当前开火判定逻辑

`Planner::plan()` 当前不是“只要有目标就 fire”。

它先看一层通用条件：

1. 参考轨迹与 MPC 实际输出的跟踪误差 `tracking_error`
2. 是否小于 `fire_thresh`

这对应的是：

```text
控制器已经跟上参考轨迹，才允许开火
```

### 9.10 前哨专用 fire gate

前哨现在还有第二层专用 fire gate。

除了跟踪误差满足条件外，还要求：

1. 选板来自有效的小陀螺窗口，或目标还没跳板
2. 命中时刻迭代收敛
3. 选中板的 `selected_delta_angle` 落在更紧的相位窗口内

这里有一个很关键的当前实现细节：

1. 轨迹连续性允许在板间空窗阶段继续跟最近板
2. 但 fire 不会在这个“过渡板位”上轻易放开

这就是为什么当前 `Planner` 的前哨策略，比 `Aimer` 更适合做稳定验收。

## 10. 当前工程里最值得记住的实现事实

### 10.1 前哨特化主要不在检测层

真正决定前哨效果的重点是：

1. `Target`
2. `Tracker`
3. `Planner`

而不是 detector 本身。

### 10.2 当前最完整的前哨链在 MPC 分支

原因是它已经具备：

1. 三板模型
2. 高度偏移
3. 固定中心旋转模型
4. 角速度锁
5. `id + offset` 联合匹配
6. 命中时刻固定点迭代
7. 前哨专用延迟
8. 前哨专用 `z` 补偿
9. 更严格的 fire 相位门

### 10.3 `Aimer` 与 `Planner` 的前哨策略并不完全一致

当前最典型的差异是：

1. `Aimer`
   前哨窗口还是硬编码 `70°/30°`
2. `Planner`
   已参数化，并且 fire 还要再过更紧的相位门

所以如果以后出现：

1. 传统链能看到也能给角，但前哨命中不稳
2. MPC 链更稳，但传统链表现一般

这并不一定是 bug，也可能是两条链的前哨策略本来就不等价。

### 10.4 模块能力不等于入口接法

当前项目里一定要分清：

1. 模块是否实现了某项能力
2. 当前入口程序是否把这项能力接进主链

最典型例子就是：

1. 模块里有 `Shooter`
2. 但 `standard.cpp` 现在没有实际调用它

## 11. 结合实车验收时，应该优先看哪里

如果后面你要做实车验收，建议按问题现象分模块定位。

### 11.1 看到了板，但目标乱跳

优先检查：

1. `solver.cpp`
   是否三维解算和重投影假设稳定
2. `target.cpp`
   EKF 参数是否异常收缩、是否发散
3. `tracker.cpp`
   板位匹配是否频繁拒绝或频繁错板

### 11.2 轨迹稳定，但击发时机不对

优先检查：

1. `aimer.cpp`
   传统链选板窗口和飞行时间迭代
2. `shooter.cpp`
   传统链开火门控
3. `planner/planner.cpp`
   MPC 的 `tracking_error`、相位门、`outpost_delay_time`

### 11.3 前哨跟得住，但总打高或打低

优先检查：

1. `outpost_armor_z_offsets`
2. `outpost_fire_z_compensation`
3. `Solver` 的前哨重投影 pitch 假设

### 11.4 验收时最值得同步记录的内部量

如果你跑的是 MPC 调试入口，建议重点记录：

1. `debug_armor_id`
2. `debug_physical_armor_id`
3. `debug_used_spin_gate`
4. `debug_selected_delta_angle`
5. `debug_hit_fly_time`
6. `debug_hit_iter_count`
7. `debug_hit_converged`
8. `debug_fire_tracking_error`
9. `debug_fire_phase_ready`
10. `tracker_debug_match_score`
11. `tracker_debug_reprojection_px`
12. `tracker_debug_xy_error_m`
13. `tracker_debug_z_error_m`

这些量基本已经覆盖：

1. 看到的是哪块板
2. 匹配是不是稳定
3. 命中时刻是否收敛
4. fire 是因为什么条件没放开
