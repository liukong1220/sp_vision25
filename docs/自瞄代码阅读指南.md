# 自瞄代码阅读指南

这份文档不再只做“先看哪个文件”的导航，而是按当前 `sp_vision25` 工程真实实现，把自动瞄准链路拆成：

1. 入口程序层
2. 数据结构层
3. 检测层
4. 解算层
5. 跟踪层
6. 传统火控层
7. MPC 火控层
8. 调试与验收层

目标是让你在真正读源码时，不只是知道“去哪看”，还知道“这里到底在算什么、为什么这么算、现在项目里有哪些特殊分支”。

建议与下面两份文档配合阅读：

1. [outpost_analysis.md](./outpost_analysis.md)
   重点讲前哨专项分析与验收。
2. [autoaim_analysis](./autoaim_analysis)
   这份保留为更长篇的方案详解，适合和本指南交叉对照。

## 1. 阅读方法

建议把当前工程理解成三层：

```text
入口程序层：决定当前到底跑哪条链
算法模块层：Detector/YOLO -> Solver -> Tracker -> Aimer/Planner
调试验收层：Plotter/WebDebugger/Ballistic Debug
```

真正读代码时，请始终先回答三件事：

1. 当前入口是谁
2. 当前控制器是谁
3. 当前开火门是谁

因为在这个项目里：

1. 并不是每个入口都走 `Aimer + Shooter`
2. 也不是每个入口都走 `Planner`
3. “模块存在”不等于“当前入口实际用到了”

## 2. 第一层：先看入口，确定程序真正走哪条链

### 2.1 `src/standard.cpp`

这是当前最容易读懂的传统入口。

建议按这个顺序看：

1. `Camera camera(config_path)`
2. `YOLO detector(config_path, false)`
3. `Solver solver(config_path)`
4. `Tracker tracker(config_path, solver)`
5. `Aimer aimer(config_path)`
6. 主循环里的：
   `camera.read -> imu_at -> solver.set_R_gimbal2world -> detector.detect -> tracker.track -> aimer.aim -> cboard.send`

当前读完后，你必须明确一件事：

```text
standard.cpp 现在走的是最简 Aimer 链路，
虽然实例化了 Shooter，但没有真正调用 shooter.shoot()
```

这意味着：

1. 它适合看“识别 -> 解算 -> 跟踪 -> 瞄准角输出”
2. 但不适合当成“传统完整开火门控链路”的代表

### 2.2 `src/mt_standard.cpp`

如果你要看传统完整火控，应该优先看它。

建议重点看：

1. `detect_thread`
   负责异步采图和检测
2. 主线程
   负责模式切换、跟踪和任务分发
3. `CommandGener`
   真正串起 `Aimer + Shooter + cboard.send`

这一层读完后，你应该形成下面这个判断：

```text
传统完整自瞄链路不是看 standard.cpp，
而是看 mt_standard.cpp
```

### 2.3 `src/standard_mpc.cpp`

这条链和传统链路最大的不同，不只是“把 `Aimer` 换成了 `Planner`”，而是：

```text
感知线程和规划线程被拆开了
```

你读的时候重点看：

1. 主线程如何把 `Target` 推进 `target_queue`
2. `plan_thread` 如何从队列读取最新目标
3. `Planner::plan()` 输出的不是单个 yaw/pitch，而是一整组连续控制状态

### 2.4 `src/auto_aim_debug_mpc.cpp`

这条入口和 `standard_mpc.cpp` 共用主链，但额外包了一层调试外壳。

重点看：

1. `Planner` 的哪些 `debug_*` 字段被拿出来画图
2. WebDebugger 如何接入运行时参数
3. 哪些调试量专门服务前哨验收

读完这条入口后，你应该知道：

```text
auto_aim_debug_mpc.cpp = MPC 主链 + 调试与验收外壳
```

### 2.5 `src/uav.cpp` / `src/sentry*.cpp`

这几条链路不是你理解步兵主链的第一优先级，但有两个价值：

1. 它们是真正把 `Shooter::shoot()` 用起来的代表
2. 可以帮助你区分“模块能力”和“入口实际接法”

例如：

1. `uav.cpp`
   传统 `Detector -> Solver -> Tracker -> Aimer -> Shooter`
2. `sentry.cpp`
   除了自瞄本身，还有全向感知与目标优先级切换

## 3. 第二层：数据结构，先看清楚每一层到底在传什么

### 3.1 `tasks/auto_aim/armor.hpp`

这是整个自瞄链路里最应该优先读的数据结构文件。

先看这几组枚举：

1. `Color`
2. `ArmorType`
3. `ArmorName`
4. `ArmorPriority`

再看 `armor_properties`。

这里非常关键的一点是：

1. 前哨在当前工程里就是 `ArmorName::outpost`
2. 在类型上属于 `small`

也就是说，检测层不会专门构造一个“前哨整体目标结构体”，而只是识别出：

```text
这是一块 outpost 装甲板
```

### 3.2 `Armor`

`Armor` 是检测和跟踪之间的统一中间表示，里面同时放了：

1. 2D 信息：
   - 角点 `points`
   - 中心 `center`
   - 框 `box`
   - 类别 `name`
   - 类型 `type`
   - 颜色 `color`
   - 置信度 `confidence`
2. 3D 信息：
   - `xyz_in_gimbal`
   - `xyz_in_world`
   - `ypr_in_world`
   - `ypd_in_world`

因此你可以把它理解成：

```text
Armor = 检测结果 + 空间解算结果
```

### 3.3 `Target`

`Target` 是 `Tracker` 输出给 `Aimer/Planner` 的统一目标状态对象。

它内部是一套 11 维 EKF：

```text
x = [cx, vcx, cy, vcy, cz, vcz, yaw, vyaw, r, l, h]
```

对普通目标：

1. `r, l, h` 表示半径、长短半径差和高度差

对前哨：

1. 状态形式仍然共用
2. 但三板真实高度主要不靠 `h`
3. 而是靠 `outpost_armor_z_offsets`

### 3.4 `io::Command` 与 `Plan`

这里一定要区分：

1. `io::Command`
   传统火控使用，只包含 `control/shoot/yaw/pitch`
2. `Plan`
   MPC 使用，包含：
   `yaw/pitch`
   `yaw_vel/pitch_vel`
   `yaw_acc/pitch_acc`
   `target_yaw/target_pitch`
   `fire`

因此：

```text
Aimer 输出的是点命令
Planner 输出的是轨迹中点对应的控制状态
```

## 4. 第三层：检测算法，普通装甲板和前哨是怎么被识别出来的

### 4.1 `tasks/auto_aim/yolo.cpp`

这个文件只是一个分发器，根据配置里的 `yolo_name` 选择：

1. `YOLOV5`
2. `YOLOV8`
3. `YOLO11`

当前主配置 `configs/standard3.yaml` 主用的是：

```yaml
yolo_name: yolov5
use_traditional: true
```

所以你真正该优先读的是 `yolos/yolov5.cpp`。

### 4.2 `tasks/auto_aim/yolos/yolov5.cpp`

当前工程主检测分支的核心逻辑在这里。

建议重点看 `detect()` 和 `parse()`。

整个流程是：

1. 根据 `use_roi` 决定是否裁图
2. 将图像缩放到 `640 x 640`
3. OpenVINO 推理
4. 读取每一行输出：
   - 置信度
   - 颜色类别
   - 编号类别
   - 4 个角点
5. NMS 去重
6. 构造 `Armor`
7. 依次经过：
   - `check_name()`
   - `check_type()`
   - 可选 `use_traditional_` 二次角点矫正

这里要注意两个算法细节：

1. `check_name()`
   会过滤 `not_armor` 和低置信度目标
2. `check_type()`
   会检查编号和大小装甲板是否匹配

对前哨尤其重要的一点是：

1. `outpost` 在这里不会进入大装甲板合法集合
2. 也就是说，它在几何模板上始终按小装甲板处理

### 4.3 `tasks/auto_aim/detector.cpp`

如果你还想理解传统视觉链路，再看这个文件。

它做的是：

1. 灰度化
2. 二值化
3. 轮廓提取
4. 灯条筛选
5. 灯条配对
6. 图案分类
7. 重叠装甲板消歧

在当前工程里，它主要有两种作用：

1. 独立传统方案
2. 给 `YOLOV5` 做二次角点矫正

### 4.4 当前检测层对前哨的真实作用

检测层对前哨真正做的事情只有三件：

1. 识别成 `ArmorName::outpost`
2. 给出稳定角点
3. 交给后续 `Solver/Tracker`

也就是说，前哨难点的主体不在 detector，而在后面的：

1. 几何恢复
2. 跟踪匹配
3. 选板与开火时机

## 5. 第四层：解算算法，2D 角点是怎么变成 3D 观测的

### 5.1 `tasks/auto_aim/solver.cpp`

这是从像素世界进入几何世界的关键桥梁。

建议按下面顺序读：

1. 构造函数
2. `set_R_gimbal2world()`
3. `solve()`
4. `reproject_armor()`
5. `optimize_yaw()`

### 5.2 解算主链

`solve()` 里真正发生的步骤是：

1. 根据装甲板类型选择模板点：
   - `BIG_ARMOR_POINTS`
   - `SMALL_ARMOR_POINTS`
2. 用 `cv::solvePnP(..., SOLVEPNP_IPPE)`
3. 得到相机坐标下的 `tvec`
4. 通过：
   `camera -> gimbal -> world`
   完成坐标变换
5. 得到：
   - `xyz_in_world`
   - `ypr_in_world`
   - `ypd_in_world`
6. 对非平衡目标继续做 `optimize_yaw()`

### 5.3 `optimize_yaw()` 在做什么

这一步不是重新做一次 PnP，而是：

1. 在一个 `yaw` 搜索范围内遍历候选姿态
2. 对每个候选姿态做重投影
3. 选取重投影误差最小的 `yaw`

可以把它理解成：

```text
先用 PnP 得到一个姿态，
再用几何重投影把 yaw 修得更稳定
```

### 5.4 前哨在解算层的特殊点

最关键的是 `reproject_armor()` 里的固定 pitch 假设：

```text
outpost      -> pitch = -15°
普通装甲板   -> pitch = +15°
```

这件事会直接影响：

1. 重投影误差
2. tracker 匹配
3. 后续空间位置估计

所以当前工程里前哨并不是“普通小装甲板换个标签”，它从几何重投影开始就已经分叉。

## 6. 第五层：跟踪算法，这是当前工程分叉最明显的地方

### 6.1 `tasks/auto_aim/tracker.cpp`

这个文件建议你至少看两遍。

第一遍只看流程：

1. `track()`
2. `state_machine()`
3. `set_target()`
4. `update_target()`

第二遍专看前哨：

1. `select_best_outpost_match()`
2. `accept_outpost_match()`

### 6.2 跟踪状态机

当前状态机包括：

1. `lost`
2. `detecting`
3. `tracking`
4. `temp_lost`
5. `switching`

最核心的行为是：

1. `lost -> detecting`
   找到初始目标
2. `detecting -> tracking`
   连续命中达到 `min_detect_count`
3. `tracking -> temp_lost`
   当前帧没匹配上
4. `temp_lost -> lost`
   丢失超过容忍阈值

前哨额外有一条专门逻辑：

1. `temp_lost` 阈值切到 `outpost_max_temp_lost_count`
2. 让前哨比普通目标更抗短时丢板

### 6.3 `set_target()`：目标初始化

这一段决定当前目标被初始化成几板模型。

当前规则是：

1. 平衡步兵：
   2 板模型
2. 前哨：
   3 板模型
3. 基地：
   3 板模型
4. 其他普通目标：
   4 板模型

因此当前工程同时存在三类旋转体：

```text
2 板：平衡
3 板：前哨 / 基地
4 板：普通目标
```

### 6.4 `Target` 内部状态与预测

`target.cpp` 里的 `predict()` 是当前目标运动学假设真正落地的地方。

统一状态是：

```text
x = [cx, vcx, cy, vcy, cz, vcz, yaw, vyaw, r, l, h]
```

但不同目标的预测方式不同。

#### 普通目标

使用常速度模型：

1. 中心位置按速度积分
2. `yaw` 按 `vyaw` 积分
3. 过程噪声较大

#### 前哨目标

有两种模式：

1. 固定中心旋转模型
   - `vx/vy/vz` 压回 0
   - 中心不平移
   - 只保留相位转动
   - 过程噪声更小
2. 普通常速度模型
   - 如果关闭固定中心模式，则退回常速度

此外，前哨还有：

1. 收敛后角速度锁
2. 当 `|vyaw| > 2` 且已收敛时，锁到 `±outpost_spin_speed_lock`

### 6.5 `Target::update_ypda()`：观测模型

这一段是 EKF 观测更新的核心。

观测量定义为：

```text
z = [yaw_los, pitch_los, distance, armor_yaw]
```

来源分别是：

1. `armor.ypd_in_world`
2. `armor.ypr_in_world[0]`

观测噪声不是完全固定的，而是随相位和距离做了轻量经验调节。

### 6.6 普通目标的关联

普通目标的更新策略大体是：

1. 先预测当前 `target_`
2. 筛出同名同类型候选
3. 对候选 `solver.solve()`
4. 调 `target_.update(armor)`

而 `target_.update()` 内部会：

1. 展开理论装甲板列表 `armor_xyza_list()`
2. 优先看几块距离较近的理论板
3. 用：
   - 装甲板 yaw 差
   - 视线 yaw 差
   做代价函数
4. 选出最匹配的板号

### 6.7 前哨的专用匹配

这是当前工程里前哨最“像专项算法”的一段。

前哨不会直接走普通目标的默认关联，而是先执行：

```text
select_best_outpost_match()
```

它会同时枚举：

1. 当前局部板号 `id`
2. 物理板号偏移 `offset`

然后对每种组合计算综合代价，代价包含：

1. 重投影误差
2. 视线 yaw 误差
3. pitch 误差
4. 距离误差
5. 装甲板 yaw 误差
6. xy 位置误差
7. z 位置误差
8. 连续性惩罚

最后再通过 `accept_outpost_match()` 做门限筛选。

### 6.8 前哨为什么要有 `offset`

这部分一定要彻底看懂。

前哨当前引入了两个概念：

1. `local armor id`
2. `physical armor id`

它们分别负责：

1. 当前理论几何序列中的第几块板
2. 真实物理上到底是高板、低板还是基准板

`set_armor_id_offset()` 的意义是：

1. 当匹配认为当前整体板号需要平移时
2. 只改 `offset`
3. 同时修正 `ekf_.x[4]`
4. 保证重映射前后高度连续

这一步是当前前哨三板高度建模能稳定工作的关键。

## 7. 第六层：传统火控算法

### 7.1 `tasks/auto_aim/aimer.cpp`

先看 `aim()`，再看 `choose_aim_point()`。

#### `aim()` 的工作过程

它会做：

1. 根据 `decision_speed` 选择高低速延迟
2. 预测目标到当前决策时刻
3. 选出当前要打的装甲板
4. 用 `tools::Trajectory` 估一次飞行时间
5. 再做最多 10 次固定点式迭代：
   - 预测到命中时刻
   - 重选板
   - 重算飞行时间
6. 输出最终 `yaw/pitch`

#### `choose_aim_point()` 的选板逻辑

当前逻辑是：

1. 如果 `target.jumped == false`
   直接打当前观测板
2. 非小陀螺时
   在可见角内尽量锁住当前板
3. 小陀螺时
   按 `comingngle/ leaving_angle` 找进入窗口的板
4. 若窗口内找不到
   退化到 `fallback_to_closest()`

### 7.2 `Aimer` 对前哨的现状

这里必须明确一点：

1. `Aimer` 现在会把前哨强制视为 spin gate 目标
2. 但前哨窗口仍然是硬编码 `70° / 30°`

也就是说：

```text
Aimer 能打前哨，
但它对前哨的支持没有 Planner 那么完整
```

### 7.3 `tasks/auto_aim/shooter.cpp`

这个文件很短，但不要跳过。

它是传统链路里的最后一道安全门，核心逻辑是：

1. `command.control == true`
2. `targets` 非空
3. `auto_fire == true`
4. 当前命令相对上一帧不能突变太大
5. 当前云台角要接近上一帧命令
6. `aimer.debug_aim_point.valid == true`

只有这样才允许 `shoot=true`。

但是一定要再次记住：

1. 模块里有 `Shooter`
2. 不等于每个入口都调用了 `Shooter`

## 8. 第七层：MPC 火控算法

### 8.1 `tasks/auto_aim/planner/planner.cpp`

如果你当前最关心的是前哨和命中率，`planner.cpp` 的优先级和 `tracker.cpp` 是一样高的。

建议按下面顺序读：

1. 常量与 `AimSelection`
2. `choose_aim_selection()`
3. `solve_hit_target()`
4. `plan(std::optional<Target>)`
5. `plan(Target)`
6. `resolve_angle_window()`
7. `resolve_delay_time()`
8. `resolve_aim_xyz()`
9. `get_trajectory()`

### 8.2 `Planner` 的总流程

当前 `Planner` 做的事情可以概括为：

1. 先按延迟预测目标
2. 再做命中时刻固定点迭代
3. 用命中时刻目标生成参考轨迹
4. 分别对 yaw / pitch 解 `TinyMPC`
5. 最后做 `fire` 判定

### 8.3 `choose_aim_selection()` 在做什么

它本质上是在回答：

```text
当前参考控制应该跟哪块板
```

当前逻辑包括：

1. 未发生真实跳板时
   更信当前观测板
2. 非小陀螺时
   在正常可见角里尽量锁板
3. 小陀螺或前哨时
   用 spin gate 策略选“正在进入窗口”的板
4. 如果窗口里没有
   fallback 到最近板，优先保证参考连续

### 8.4 `solve_hit_target()` 在做什么

这是当前 `Planner` 比传统 `Aimer` 更强的一步。

它会做：

```text
选板 -> 算飞行时间 -> 预测到命中时刻 -> 再选板
```

直到：

1. 飞行时间变化足够小
2. 板号也稳定

才认为命中时刻求解收敛。

### 8.5 `get_trajectory()` 在做什么

这里不是简单把当前点重复复制，而是：

1. 把目标回滚到轨迹起点
2. 沿未来地平线逐帧预测
3. 每帧重新求 `yaw/pitch`
4. 用中心差分估速度
5. 对切板尖峰做轻量抑制

所以当前 MPC 不是在追单点，而是在追一条参考轨迹。

### 8.6 前哨在 `Planner` 里的专用支持

前哨在当前 `Planner` 里已经有一套比较完整的专用逻辑：

1. `outpost_coming_angle`
2. `outpost_leaving_angle`
3. `outpost_delay_time`
4. `outpost_fire_z_compensation`
5. 命中时刻固定点迭代
6. 前哨专用开火相位门

相对 `Aimer`，它真正多出来的不是一个参数，而是一整套：

```text
前哨选板 -> 命中时刻求解 -> 轨迹 -> 开火门
```

### 8.7 `Planner.fire` 到底怎么判

普通目标：

1. 主要看 `tracking_error < fire_thresh`

前哨目标：

1. 先看 `tracking_error < fire_thresh`
2. 再看 `hit_solution.converged == true`
3. 再看命中时刻相位角是否落入更紧的击打窗口
4. 如果已经 `jumped`，还必须是真正通过 `spin gate` 选中的板
5. 仅靠 fallback 维持参考连续的板，不允许开火

这就是当前前哨能减少“中一发空一发”的关键收口。

## 9. 第八层：调试、可视化与验收

### 9.1 `src/auto_aim_debug_mpc.cpp`

这条入口最重要的价值，不是“多了个界面”，而是它把算法内部状态显式暴露出来了。

当前你最应该看的调试量包括：

1. `planner_selected_armor`
2. `planner_selected_physical_armor`
3. `planner_hit_fly_time_ms`
4. `planner_hit_iters`
5. `planner_hit_converged`
6. `planner_selected_delta_deg`
7. `planner_fire_phase_limit_deg`
8. `planner_fire_phase_ready`
9. `planner_spin_gate`
10. `tracker_match_valid`
11. `tracker_match_score`
12. `tracker_reprojection_px`

### 9.2 这些调试量分别在回答什么

1. `tracker_match_valid`
   跟踪匹配是否靠谱
2. `planner_selected_physical_armor`
   当前到底在打哪块物理板
3. `planner_hit_converged`
   命中时刻假设是否稳定
4. `planner_selected_delta_deg`
   板在命中时刻的相位是否合适
5. `planner_fire_phase_ready`
   不开火到底是因为相位不对，还是因为别的条件没过

### 9.3 当前验收时的推荐观察顺序

如果你现在上车验收，建议按下面顺序看：

1. 识别是否稳
   `outpost` 是否稳定识别成正确类别
2. 跟踪是否稳
   `tracker_match_valid`
3. 物理板号是否对
   `planner_selected_physical_armor`
4. 命中时刻是否稳
   `planner_hit_converged`
5. 相位是否落窗
   `planner_selected_delta_deg`
   `planner_fire_phase_ready`
6. 最后再调：
   `outpost_delay_time`
   `outpost_fire_z_compensation`
