# 运行入口与文件关系

这份文档只回答一件事：当前 `src/` 里有哪些真正会跑起来的入口程序，它们分别调了哪些算法链路，以及现在更适合把哪一个当主入口来理解和验收。

## 1. 先看结论

当前工程没有唯一的“总主程序”，而是按机器人形态和控制方式分成几条主链：

1. 步兵/标准车，传统火控：
   `src/standard.cpp`
   `src/mt_standard.cpp`
2. 步兵/标准车，MPC 火控：
   `src/standard_mpc.cpp`
   `src/auto_aim_debug_mpc.cpp`
3. 无人机：
   `src/uav.cpp`
   `src/uav_debug.cpp`
4. 哨兵：
   `src/sentry.cpp`
   `src/sentry_bp.cpp`
   `src/sentry_debug.cpp`
   `src/sentry_multithread.cpp`

如果你现在的重点是：

1. 看当前项目最完整的前哨与 MPC 自瞄链路，优先读 `standard_mpc.cpp` 和 `auto_aim_debug_mpc.cpp`
2. 看最简单的传统自瞄链路，优先读 `standard.cpp`
3. 看标准车实战多线程链路，优先读 `mt_standard.cpp`

## 2. 当前最值得优先看的入口

### 2.1 `src/standard.cpp`

这是最短、最容易读懂的一条传统自瞄入口，主链路是：

```text
Camera
  -> YOLO
  -> Solver
  -> Tracker
  -> Aimer
  -> CBoard.send(command)
```

要特别注意一件事：

1. 当前文件虽然实例化了 `Shooter`
2. 但没有真正调用 `shooter.shoot()`

所以它现在更像“单线程瞄准角输出入口”，而不是完整传统开火门控入口。

### 2.2 `src/mt_standard.cpp`

这是当前标准车更接近实战部署的传统链路，特点是：

1. 多线程检测
2. `CommandGener` 异步发指令
3. 自瞄与打符同程序内切换
4. 这条链路才真正把 `Aimer + Shooter` 串起来

如果你想看：

```text
传统自瞄如何完整做到“识别 -> 跟踪 -> 瞄准 -> 开火”
```

优先看它。

### 2.3 `src/standard_mpc.cpp`

这是标准车 MPC 主程序，主链路是：

```text
感知线程：Camera -> YOLO -> Solver -> Tracker -> Target队列
规划线程：Target队列 -> Planner -> Gimbal.send(...)
```

特点：

1. 通信侧改为 `io::Gimbal`
2. 控制侧改为 `Planner`
3. 输出不是单个 `yaw/pitch`，而是一整组连续控制状态
4. 同时保留打符模式

### 2.4 `src/auto_aim_debug_mpc.cpp`

这是当前前哨与 MPC 调参与验收最重要的入口。

它在 `standard_mpc.cpp` 的基础上增加了：

1. Web 调试器
2. Ballistic Debug 面板
3. `tracker` 和 `planner` 的内部调试量
4. 运行时参数热更新入口

因此，如果你现在要做：

1. 前哨算法验收
2. 相位、延迟、MPC 参数定位
3. 实车问题复盘

优先看它。

## 3. `src/` 里各入口的作用

| 文件 | 当前定位 | 控制方案 | 通信接口 | 备注 |
|---|---|---|---|---|
| `standard.cpp` | 最简传统自瞄入口 | `Aimer` | `CBoard` | 当前未调用 `Shooter::shoot()` |
| `mt_standard.cpp` | 标准车传统实战入口 | `Aimer + Shooter` | `CBoard` | 多线程检测与异步发指令 |
| `standard_mpc.cpp` | 标准车 MPC 主程序 | `Planner` | `Gimbal` | 含打符模式 |
| `auto_aim_debug_mpc.cpp` | MPC/前哨专项调试入口 | `Planner` | `Gimbal` | 调试量最全 |
| `mt_auto_aim_debug.cpp` | 传统链路调试入口 | `Aimer + Shooter` | `CBoard` | 更偏跟踪与重投影调试 |
| `uav.cpp` | 无人机主程序 | `Aimer + Shooter` | `CBoard` | 以传统 `Detector` 为主 |
| `uav_debug.cpp` | 无人机调试入口 | `Aimer + Shooter` | `CBoard` | 有更多可视化与曲线 |
| `auto_buff_debug.cpp` | 打符调试入口 | `Buff_Aimer` | `CBoard` | 非自瞄主链 |
| `auto_buff_debug_mpc.cpp` | 打符 MPC 调试入口 | `Buff_Aimer(mpc)` | `Gimbal` | 非自瞄主链 |
| `sentry.cpp` | 哨兵主程序 | `Aimer + Shooter` | `CBoard`/ROS2 | 有全向感知切换 |
| `sentry_bp.cpp` | 哨兵分支入口 | `Aimer + Shooter` | `CBoard`/ROS2 | 后相机感知变体 |
| `sentry_debug.cpp` | 哨兵调试入口 | `Aimer + Shooter` | `CBoard`/ROS2 | 可视化更强 |
| `sentry_multithread.cpp` | 哨兵多摄并行入口 | `Aimer + Shooter` | `CBoard`/ROS2 | 决策复杂度最高 |

## 4. 当前最重要的几条调用关系

### 4.1 传统单线程链路

对应 `standard.cpp`：

```text
相机图像
  -> YOLO.detect
  -> Solver.set_R_gimbal2world
  -> Tracker.track
  -> Aimer.aim
  -> CBoard.send
```

### 4.2 传统多线程链路

对应 `mt_standard.cpp`：

```text
detect_thread
  -> MultiThreadDetector
主线程
  -> Tracker.track
  -> CommandGener.push
CommandGener 线程
  -> Aimer.aim
  -> Shooter.shoot
  -> CBoard.send
```

### 4.3 MPC 链路

对应 `standard_mpc.cpp` / `auto_aim_debug_mpc.cpp`：

```text
主线程
  -> YOLO.detect
  -> Solver
  -> Tracker
  -> target_queue.push
plan_thread
  -> Planner.plan
  -> Gimbal.send
```

1. 想快速理解项目结构：
   先看 `standard.cpp`

## 7. 看门狗脚本怎么选

当前项目已经把“调试型入口”和“比赛型入口”的看门狗脚本分开。

### 7.1 `debug_mpc_watchdog.sh`

适用场景：

1. 你需要 WebDebugger
2. 你需要浏览器自动打开
3. 你需要看 Plot / Ballistic Debug / 调试覆盖层
4. 你跑的是 debug 程序，而不是比赛主程序

典型对象：

1. `auto_aim_debug_mpc`
2. `auto_debug`
3. `sentry_debug`

典型启动方式：

```bash
./debug_mpc_watchdog.sh
./debug_mpc_watchdog.sh auto_debug configs/standard3.yaml
./debug_mpc_watchdog.sh sentry_debug configs/sentry.yaml
```

要点：

1. 默认主程序是 `build/auto_aim_debug_mpc`
2. 它会等待 Web 服务就绪后自动开浏览器
3. 它更适合调参与验收，不适合比赛时追求最小额外开销

### 7.2 `run_with_watchdog.sh`

适用场景：

1. 你要跑比赛主入口
2. 不需要浏览器和 Web 调试
3. 想尽量减少调试附带开销
4. 只关心“程序退出后自动拉起”

典型对象：

1. `standard_mpc`
2. `sentry`
3. `standard`
4. `mt_standard`

典型启动方式：

```bash
./run_with_watchdog.sh
./run_with_watchdog.sh standard_mpc configs/standard3.yaml
./run_with_watchdog.sh sentry configs/sentry.yaml
```

要点：

1. 默认主程序是 `build/standard_mpc`
2. 默认配置会随主程序切换：
   `standard_mpc -> configs/standard3.yaml`
   `sentry -> configs/sentry.yaml`
3. 它不会自动打开浏览器，也不会等待 Web 服务

### 7.3 两类脚本的职责边界

这点一定要讲清楚，避免后续误用。

`debug_mpc_watchdog.sh` 负责：

1. 启动 debug 程序
2. 自动拉起浏览器
3. 适配网页调试与可视化验收

`run_with_watchdog.sh` 负责：

1. 启动比赛主程序
2. 程序退出后自动重启
3. 不额外附带调试网页逻辑

### 7.4 串口异常时，看门狗和程序内部恢复怎么配合

当前项目在 `io/gimbal/gimbal.cpp` 中已经补了串口断开后的内部重连逻辑。

因此：

1. 如果串口短时断开，但主进程仍存活
   优先由程序内部重连恢复
2. 如果程序因为其他原因直接退出
   再由对应 watchdog 脚本自动拉起

换句话说：

```text
串口异常恢复的第一层是程序内部重连，
watchdog 负责的是“进程退出后自动重启”，不是代替内部重连。
```

最重要的一条经验是：

```text
先确认你现在跑的是哪条入口，再去判断算法行为；
否则很容易把 Aimer 问题、Planner 问题和入口接线问题混在一起。
```
